# Development

The full repo is the plugin. Claude Code loads the hooks module from `hooks/hooks.json`.

## Layout

| Path | What it contains |
| --- | --- |
| `.claude-plugin/` | The plugin manifest (`plugin.json`) and the marketplace manifest. |
| `hooks/register.tsx` | The hooks, the classifier calls, the notes for later prompts, `/loadout` and its pane. |
| `hooks/scope.ts` | Pure helpers: parse a listing, group its items, rebuild it with a note. |
| `types/index.d.ts` | The state that the plugin keeps for a session. |
| `tests/` | The tests of the hooks, the checks for docs and versions, and a smoke test with real Claude Code. |
| `tests/session.mjs` | Starts one real Claude Code session with the plugin and the fake MCP servers. |
| `evals/` | The impact eval: the tasks, the fixed setup of servers and skills, and the runner. |
| `.claude/skills/verify/` | The recipe that `/verify` reads: how to drive the plugin in real Claude Code. |
| `docs/` | The user docs, and the banner and logo in `docs/assets/`. |

## Verification loop

Do these steps before each commit, in this order. If a step changes code, start again at step 1. The full rules
are in `CODING_STANDARDS.md`.

1. Run `/simplify`. This built-in skill cleans up the diff and applies the fixes.
2. Run `/code-review`. This built-in skill looks for bugs in the diff. Fix each bug that it finds. If you do not
   fix a finding, write the reason in the commit message.
3. Run the three checks in [Checks](#checks).
4. Run `/verify` after a change to `hooks/`, `types/` or `.claude-plugin/plugin.json`. This built-in skill drives
   the change end to end in real Claude Code. It reads the recipe in `.claude/skills/verify/`. Skip this step when
   the diff changes only tests or docs.

To drive the plugin yourself, run `.claude/skills/verify/drive.mjs` with one or more prompts. Each prompt goes into
one headless session after the reply to the prompt before it. The script prints the decisions of the plugin, the
notes, the tool calls and the token use of each request:

```bash
node .claude/skills/verify/drive.mjs run 'List the open issues of project OPS.' '/loadout'
```

## Checks

Run all three checks before each commit:

```bash
claude plugin validate .
```

```bash
claude plugin test .
```

```bash
node tests/docs.check.mjs
```

- `claude plugin validate .` reads the manifests and the hooks module as Claude Code does.
- `claude plugin test .` tests the hooks with a fake host. The tests replace the Haiku call with a fixed reply.
- `tests/docs.check.mjs` checks the rules for the docs.

CI (`.github/workflows/test.yml`) runs the three checks for each push to `main` and each pull request:

- It runs `claude plugin test .` with a fixed Claude Code version. To use a newer version, run the tests with it on
  your machine first. Then change the version in the workflow.
- Each Monday, it also runs `claude plugin test .` with the newest Claude Code release. If this job fails, a new
  release changed something that the plugin uses. Fix the plugin, then increase the fixed version.
- For each pull request, it runs `tests/version.check.mjs`. This check fails if the plugin changed and its version
  did not increase.

### Smoke test

The smoke test runs real headless Claude Code with this plugin and two fake MCP servers. One server is for the task
of the first prompt. The other server has weather tools, which the task does not need. The other tests replace
Claude Code and the classifier with fakes. This test runs all the parts together.

Run it after a change to the plugin, before a release, and after you increase the Claude Code version:

```bash
node tests/smoke.e2e.mjs
```

The test sends two prompts in one session. It checks these results:

1. The plugin changes the first tool listing, so Claude Code builds it after the first prompt.
2. The classifier keeps the tracker tools and hides the weather tools.
3. The plugin removes the instructions of the weather server.
4. The second prompt asks for the weather. It gets a note that names the weather tools.
5. Claude loads a weather tool with ToolSearch and calls it.

At the same time, the test runs a second session with tool search off. It checks that the plugin keeps the
instructions of all servers.

- It needs a logged-in Claude Code. It costs API usage, less than $0.01 with Haiku. Use `--model` to change the model.
- The checks read the trace file of the plugin and the calls to the fake servers. They do not read the reply of the
  model.
- If a check says that the model or the classifier did not do a step, run the test again. Both are models.
- A failed run keeps its folder, with the transcript and the trace. The test prints the path. To keep the folder of a
  run that passes, add `--keep`.
- CI does not run the smoke test, because CI has no login.

## Impact eval

The impact eval measures what the plugin changes in cost, speed and quality. It runs each task as a real headless
Claude Code session, one time for each arm:

| Arm | Plugin | Options |
| --- | --- | --- |
| `baseline` | Off | None |
| `loadout` | On | The defaults: the plugin changes the listings only |
| `effort` | On | `effortPerPrompt` |
| `model` | On | `modelForSession`. The eval answers the model question with the smaller model. |
| `all` | On | `effortPerPrompt` and `modelForSession` |

To see the number of sessions before you spend money, run this command:

```bash
node evals/impact.mjs --dry-run
```

To run the full eval, run this command:

```bash
node evals/impact.mjs
```

The defaults are 8 tasks, 5 arms and 2 runs: 80 sessions on Sonnet with effort `high`. With the defaults, a run
costs approximately $3 and takes approximately 5 minutes. Use these options to change the run:

| Option | Default | Meaning |
| --- | --- | --- |
| `--arms` | All five | The arms to run, separated by commas |
| `--tasks` | All | The task ids of `evals/tasks.mjs`, separated by commas |
| `--runs` | `2` | The sessions for each task and arm. Use more runs for smaller differences. |
| `--jobs` | `4` | The sessions that run at the same time |
| `--model`, `--effort` | `sonnet`, `high` | The model and the effort of each session |
| `--env` | `fixed` | `fixed` or `real`, see below |
| `--keep` | Off | Keep the folders of the sessions that pass |

The eval writes `results.jsonl` and `report.md` to `evals/results/`, which git does not track. To write the report
of a run folder again, run `node evals/impact.mjs --report <folder>`.

### What the eval measures

- Cost: the cost of the session, plus the classifier calls. The session cost does not include the classifier
  calls, so the plugin writes their token use to its trace file.
- Speed: the time from each prompt to its result. This time includes the classifier calls before the first request.
- Quality: the checks of each task. The checks read the calls to the fake servers, the files and the answers.
- The report compares each arm with the baseline for each task. Then it takes the geometric mean over the tasks.

The first session that sends the system prompt and the tools writes them to the prompt cache. The next sessions
read them for less money. Thus, before the measured runs, the eval runs one session for each arm.

### Fixed setup or real setup

The plugin saves more when the listings are longer. Thus the result depends on the setup of the session.

- `--env fixed` uses a fixed setup: 12 fake MCP servers with approximately 80 tools, and 40 project skills. The
  session does not load your user settings, plugins, skills or MCP servers. The policy settings of your organization
  still apply. Use this setup to compare two versions of the plugin.
- `--env real` also loads your own settings, plugins, skills and MCP servers. Use this setup to see the savings on
  your machine. The eval turns off an installed copy of loadout in each arm.

## Type check

To develop with the engine types in your editor, load the plugin one time with `claude --plugin-dir .`. Claude Code
then writes `.claude-plugin/types/`, which `tsconfig.json` uses. Git does not track this folder. Without it, `tsc`
fails with TS2688. To check the types, run this command:

```bash
npx -p typescript tsc -p tsconfig.json
```

CI does not run the type check. Claude Code writes the types only in a session that is logged in, and CI has no
login.

## Try a change

1. Install the plugin from your clone. See [Run from a local folder](./installation.mdx#run-from-a-local-folder).
2. Change a file.
3. Run `/reload-plugins` in an open session, or start a new session.
4. Type `/loadout` to see the result.

## Release

1. Increase `version` in `.claude-plugin/plugin.json`. Claude Code caches a plugin by its version, so without a new
   version, users do not get the change.
2. Run the three checks and the smoke test.
3. Optional: run `node tests/version.check.mjs` to do the version check of CI before you push.
